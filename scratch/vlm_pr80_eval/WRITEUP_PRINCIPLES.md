# Write-up principles

The main reader is technically capable but has not been living inside the experiment.

Human readers can be smart and still get overloaded quickly. Write to make the information easy to take in.

- Use simple words where simple words will do.
- Use progressive disclosure: answer first, then enough evidence to judge the answer, then detail only where it matters.
- Apply that rule at every level: word, sentence, paragraph, section and whole document.
- Prefer one main claim per sentence and one main point per paragraph.
- Use normal-person language. Avoid project-management register and experiment-internal jargon unless it is genuinely the clearest term.
- Define a term before relying on it.
- Prefer concrete counts before percentages when that makes the result easier to understand.
- Say what the model saw, what it was asked, what was scored, and what happened.
- Keep local model scores separate from end-to-end pipeline results.
- State limits where they first affect interpretation.
- Do not achieve brevity by inventing shorthand.
- Name the model when a result applies to only one model. Do not turn a one-model result into a claim about both models.
- Do not claim that one changed variable caused a result when the experiment changed several things at once.
- Organise explanatory reports around result → evidence → limits → decision, not around a chronological work diary.
- Use plots or diagrams only when they make the result easier to understand than prose. Give each visual one clear message, plain labels and a caption that says what matters.
- Move exhaustive parameter grids, hashes, prompts and reproduction detail into supporting files when they would interrupt the main reading flow.

A technically complete document that is cognitively heavy has not passed.
